Part one

Using the tool

Written for someone who has never opened the code. You need a match video, a PowerShell window, and about twenty minutes the first time. After that a new match takes two or three.

What it does, in one paragraph

You give it a video of a squash match shot from a fixed camera behind the court. It finds the two players in every frame, follows them, works out where their feet are on the actual floor in metres, and can then split the match into rallies. It writes annotated videos you can watch to check it, and CSV files you can put in a spreadsheet. It runs on an ordinary laptop CPU — there is no GPU and no neural network anywhere in it.

What it does not do. It does not track the ball — that was tried and it failed on real footage. It does not tell you who won a point from the play itself; when it needs to know, it reads the broadcast scoreboard. And it will not guess a player's name: you tell it.
01

Set it up, once

0 · Get a PowerShell window pointed at the project

Press Win and type PowerShell, then open it. It starts in your home folder, so move it to the project — open the project folder in File Explorer, click once in the address bar to select the path, copy it, and type cd followed by that path in quotes: 

cd "C:\Users\you\PycharmProjects\PythonProject"

Check you have landed in the right place:

dir

The listing must include squashvision. If it does not, you are in the wrong folder and every command below will fail with not recognized.

It has to be PowerShell. Not Command Prompt, and not Git Bash — including the terminal tab inside PyCharm, which is often set to one of those. If you are unsure which you have, run $PSVersionTable: PowerShell prints a table, the others print an error or nothing useful. In PyCharm you can switch it under Settings → Tools → Terminal → Shell path, or just use a separate PowerShell window.

Then four commands, in order.

1 · Check Python is installed

py --version

You want 3.10 or newer. If it says py is not recognized, install Python from python.org — and on the first screen of the installer tick Add python.exe to PATH. Then close PowerShell, open it again, and retry.

2 · Make the project its own Python

This creates a .venv/ folder holding a private copy of Python, so the libraries this tool needs cannot collide with anything else on your machine. 

py -m venv .venv

It prints nothing and takes a few seconds. Safe to run again — if .venv/ already exists it just refreshes it.

3 · Install the two libraries

./.venv/Scripts/python.exe -m pip install numpy opencv-python

About 60 MB of download. It should end with Successfully installed numpy… opencv-python…. If it instead says Requirement already satisfied, they were there already and you are fine.

4 · Check it runs

./.venv/Scripts/python.exe -m squashvision

That prints the list of commands. Every command in this guide starts the same way, followed by a command name, and every one accepts --help.

Two different words for Python, and they are not interchangeable. py is the launcher that comes with Windows Python — use it only for step 2, before the environment exists. After that, always ./.venv/Scripts/python.exe, which is the copy that has the libraries. Plain python is the one word to avoid: on a stock Windows install it opens the Microsoft Store instead of running anything.
Tired of typing that? Once per PowerShell window you can switch to the short form: 
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
./.venv/Scripts/Activate.ps1
After that python -m squashvision … works on its own. The first line is needed because Windows blocks scripts by default; -Scope Process means it applies only to this window and changes nothing permanently. If you skip this, just use the long form everywhere below.
Every command below is a single line. Some are long and will wrap on screen; select the whole block and paste it in one go. There is no line-continuation character to get wrong.
02

Point it at your video

Nothing is copied or converted. You pass the path to your file every time. Always put quotes around it — match filenames usually contain spaces. Start by rendering twenty seconds and looking at the result: 

./.venv/Scripts/python.exe -m squashvision demo "C:\videos\match.mp4" --start 300 --duration 20 --out output/demo.mp4

--start 300 means "begin five minutes in". Pick a moment when a rally is actually happening. Then open the result: 

start output/demo.mp4

You will see two coloured boxes following the players.

Getting the path right. The quickest way is to find the video in File Explorer, hold Shift, right-click it, and choose Copy as path — that puts the full quoted path on your clipboard, ready to paste.

It will probably be wrong the first time on a new camera. That is expected, and the next three steps are how you fix it.

03

Teach it your court — once per camera angle

The tool needs to know where the court floor is in the picture so it can convert pixels into metres. You do that by clicking on the painted lines: 

./.venv/Scripts/python.exe -m squashvision calibrate "C:\videos\match.mp4" --out profiles/mycourt.json

A window opens showing the court with the players removed. It asks for one landmark at a time — the front-left corner, the short line, the service boxes. Click near the mark to zoom in, then click again precisely. Once four are placed it draws the fitted court back over the picture, so a bad click shows up immediately as lines that do not sit on the paint.

Keys: u undo · s skip a landmark · w write and quit · q quit.

Aim for under 20 cm. The banner shows the fit error in centimetres. Anything under about 20 cm is good. This file works for every video from the same camera in the same position, so you only do this once per venue.
04

Fit the detection settings — once per camera and encode

How strongly a player stands out from the floor depends on the lighting, the video compression, and what they are wearing. A white shirt on a pale court is a much weaker signal than a navy one. This searches for settings that work: 

./.venv/Scripts/python.exe -m squashvision autotune "C:\videos\match.mp4" --out profiles/myprofile.json

It takes a few minutes. It samples several windows spread through the match, tries a grid of settings on each, and keeps whichever lets the tracker observe both players most often. It prints the top few so you can see how much difference it made.

This file does not transfer. The court calibration from step 3 works on any recording from that camera. The detection profile does not — a re-encode of the same broadcast at a different resolution needs its own. Re-run autotune whenever the file changes.
05

Say who the players are

This is the step that matters most, and it is the one only a person can do. An arena camera sees spectators standing at the glass who are the same size as a player on court — bigger, sometimes, because they are closer to the lens. The tool cannot tell them apart from the players on its own. 

./.venv/Scripts/python.exe -m squashvision roster "C:\videos\match.mp4" --profile profiles/myprofile.json --names "Smith,Jones" --out profiles/myroster.json
Pass the same --profile you will run with. The boxes offered for clicking are the boxes detection actually produces, and they change with those settings. Without it you will be clicking on the wrong things.

A window opens on the court with a yellow box around everything it can see. Then:

  • Click a player, press 1 or 2 to say which one he is.
  • Do that again at four or five different places around the court — front, back, both sides. The light changes a lot between the front wall and the back corner, and the tool stores the median of what you clicked.
  • Click anyone who is not playing — a spectator, a referee, someone walking past — and press x. That fences them off.
  • w writes the file. u undoes the last thing.

Scrub with space, the ← → arrows (2 s), and [ ] (15 s).

Two things to watch in the banner

"shirts N apart". This is how different the two players' shirts are, against how much one player's own shirt varies from click to click. If the gap is not comfortably bigger than the variation, the banner says so — their kit is too similar for colour to separate them, and more clicking will not help.

"player-sized" warnings. If you fence something that is nearly as tall as the players beside it, the banner warns you in red. You have probably clicked a player by mistake, and that fence will delete him whenever he stands there. Press u.

06

Run it again and check

Now pass all three files every time:

./.venv/Scripts/python.exe -m squashvision demo "C:\videos\match.mp4" --start 300 --duration 20 --profile profiles/myprofile.json --roster  profiles/myroster.json --out output/demo.mp4

Watch it again. What you are looking for:

  • Each box stays on the same player for the whole clip, and the names are the right way round.
  • Nothing is boxed that is not a player.
  • Where the tool is not sure, it says lost or draws corner ticks rather than a solid box — that is the honest answer, not a failure.

On the Bates vs Connecticut match this took the frames where both players were resolved from 74% to 89% on one held-out five-minute span and 76% to 91% on another.

07

Get the numbers out

Positions on the actual floor, beside the camera view:

./.venv/Scripts/python.exe -m squashvision birdseye "C:\videos\match.mp4" --start 300 --duration 20 --profile profiles/myprofile.json --roster profiles/myroster.json --calibration profiles/mycourt.json --out output/plan.mp4

That prints metres covered, average position, how much of the time each player spent in the front half, and their peak speed — which is the honest check on the smoothing. A squash player sprints at about 7 m/s. If it reads 30, the path is noise, not movement.

A CSV of every frame instead:

./.venv/Scripts/python.exe -m squashvision track "C:\videos\match.mp4" --profile profiles/myprofile.json --roster profiles/myroster.json --csv output/positions.csv

One row per analysed frame: time, both players' positions, how big they were, their shirt colour, and — importantly — whether each position was measured or coasted through a gap by the motion model.

08

Optional: rallies

Split play into rallies and check the result against the broadcast scoreboard:

./.venv/Scripts/python.exe -m squashvision rallies "C:\videos\match.mp4" --profile profiles/myprofile.json --roster profiles/myroster.json --calibration profiles/mycourt.json --scoreboard

The scoreboard is free ground truth — it changes exactly once per point. You can also fit the rally detector's own settings on it, scored on parts of the match it was not fitted to: 

./.venv/Scripts/python.exe -m squashvision train "C:\videos\match.mp4" --calibration profiles/mycourt.json --out profiles/rally_config.json
The score box is hard-coded to one broadcast. A different production draws its scoreboard somewhere else, and these two commands will find nothing. Check with ./.venv/Scripts/python.exe -m squashvision scoreboard VIDEO before relying on them.

Part two

How it works

The design, and the measurements that forced it. Most of what follows exists because something simpler was tried first and failed on real footage.

The constraint that shapes everything

There is no GPU. That rules out the usual answer — a person-detector run on every frame — and pushes the whole design toward classical computer vision: subtract a background model, keep the blobs that are the right size, and reason about the handful that survive. Everything downstream is a consequence of that one blob detector being cheap but crude.

The same approach was tried for the ball and abandoned. A ball is four pixels across; so is compression noise, so is scoreboard flicker. Nothing in the picture separates them. A player is 20 to 60 pixels wide and a simple size floor removes essentially all the clutter — which is exactly why this works for bodies and not for the ball.

Finding bodies

Every frame is shrunk to 480 pixels wide and cropped to the court, which drops the neighbouring court, the crowd above, and the burnt-in graphics. That crop is the coordinate system everything else uses.

The background is a median of 21 frames sampled across a 300-frame chunk — a median rather than an average because a player crossing the frame is an outlier, and a median ignores outliers where a mean smears them into the model. Subtracting it leaves the parts of the picture that moved.

This is also the detector's central weakness, and it explains a lot of the behaviour further down: a player who stops moving disappears. He becomes part of his own background. What survives the subtraction is whatever twitched — an arm, a racket — which is why a single frame's measurement of a near-stationary player is close to meaningless.

Following, and knowing who is who

Two constant-velocity Kalman filters carry the tracks. They are not there to chase fast movement — players only move about 4.5 px between samples against a body 20 to 60 px wide. They are there to do two other things: reject associations that are physically impossible, and say where each player is inside a single blob when the two of them merge into one.

Motion answers which body was I following. It cannot answer which player is this, and those are different problems that need different evidence on different clocks. The identity problem is where this tool has had the most failures, and it now has three defences layered on top of each other.

Before any of them: the tracker may decline to start

Seeding is the one decision made from a single frame, and the head of a recording is the worst place to make it. During a knock-up the players move slowly, so background subtraction recovers only about half of each body — limbs and edges rather than the shirt itself. On the Connecticut capture at t=0 the white-shirted player measured L=127 against his dark-shirted opponent's L=132: darker than the man he is supposed to contrast with. Taking the cheapest pairing there hands slot 0 to the wrong player and inverts every label until the accumulated evidence has seen enough to swap them back.

So a frame has to earn the right to seed, on two tests. Each candidate must lean toward its own player — nearer that shirt than the other by a margin — which refuses a frame where both bodies read as the same colour. And each must be within an absolute distance of the shirt it is being matched to, which is what leaning alone cannot do: a teammate in a maroon hoodie standing outside the court sat 64 units from one shirt and 42 from the other, so he "leaned dark" by 22 while looking like nobody at all. Frames that fail claim no position and the tracker tries the next one; the wait is reported rather than hidden.

The colour gate: nothing that far away is that player

Colour entered the association as a penalty — it made a badly-matching candidate expensive, but never impossible. That is not enough on its own, because the motion gate will happily offer up a spectator standing exactly where the player was, and a penalty can always be outweighed by being close. The result was measurable: the light-shirt slot held a detection more than 35 units from its own shirt in 9–15% of measured frames — against 3–6% for the dark slot, which is easier to pick out against a pale court — with lock-ons running up to 18 consecutive frames at a mean distance of 46 to 59.

So there is now a hard ceiling: beyond 40 units from a named shirt, a candidate is refused outright and the track coasts instead. This is the test that catches a stranger in a colour neither player is wearing — and it is the only one that can. The relative test below cannot, because such a person is far from both anchors and therefore leans toward neither. Swept over eighteen minutes:

The demo prints this number live as d= beside each player, so you can watch identity being checked rather than assumed.

Refusing a candidate — and when not to

Defence 2 has a sharp edge, and pointing it the wrong way made things worse rather than better. Applied on every frame, it vetoed the tracked player himself: the light-shirted player's single-frame reading regularly comes out darker than his opponent's, trips the ratio, and gets refused. The visible symptom was the tool appearing to ignore him entirely.

It now applies only to a track that is already coasting — which is the only moment adopting a stranger is a risk, because the track has lost its player. Measured over three spans of play totalling eight minutes (a fourth span turned out to be a between-games break and is excluded — see below):

Veto applies Light-shirt measurements Both players Implausible jumps
on every frame2,34890.4%74
never2,71291.0%96

Vetoing always costs about a fifth of one player's data. Never vetoing gives that back but lets a coasting track sit on a spectator for around a second. Restricting it to coasting tracks keeps nearly all the measurements and still refuses the spectator. The frames it does decline are reported as coasted, so what is given up stays visible rather than becoming silently wrong.

A fourth defence: giving up a track that has settled on furniture

The obvious rule — "a track that stops moving is not on a player" — is wrong on its own, and measurably so. A differencing detector does not stop seeing a player who stands still, and players stand still often: during the Connecticut knock-up the real dark-shirted player held one spot for six seconds, 47 consecutive measurements with 1.8 px of wander, while his partner hit. Stillness alone would have deleted him.

What separates the two is stillness plus not looking like the man the track is named for. Across 1459 three-second windows, 227 of them nearly stationary, the distance from the track's own shirt inside a stationary window is bimodal — p75 of 8.7 against a p90 of 35.1. The lower mode is players pausing between rallies; the upper is a track sitting on somebody at the near glass. Requiring both conditions fired in exactly two places across eighteen minutes, and both were spectators.

Getting onto the floor

A homography — fitted from the landmarks you clicked in step 3 — maps the image plane to the court plane. What gets mapped matters more than it looks. Not the centre of the blob, which floats at chest height and has no fixed relationship to the ground, but a foot contact point: the horizontal centre of the whole silhouette paired with its lowest row.

Both halves of that were picked by measurement and both are counter-intuitive. Taking the horizontal position from the feet themselves is markedly worse, because feet swing back and forth with every stride while the body's centroid does not. And a coasted position is never projected at all — its box is synthesised from a remembered size, so its bottom edge is a guess, and projecting a guess produces a confident-looking court position that no pixels support.

Rallies, and the honesty problem

Rally boundaries come from movement: a short window of averaged speed for both players, and a stretch of quiet long enough to be a real break. There was also a "serve formation" term — one player in a service box, the other diagonally opposite — and it is switched off by default. That is worth explaining, because it is the clearest example of the discipline the codebase tries to keep.

The formation term looked excellent at first: F1 0.92 against 0.79 for speed alone. But that sweep scored on the same points it had been fitted to. Under held-out scoring it reverses — speed alone 0.85, with the formation term 0.71. The service boxes cover a large part of the back court, so players stand in one mid-rally all the time and the term invents breaks. The knob still exists and train still searches it; it just defaults to off.

That is why train splits the match into contiguous time blocks and scores each fold on blocks it did not fit on. It prints both numbers and labels the optimistic one as such. The saved config file records both, with a note saying which to quote.

Where the labels come from

A broadcast scoreboard changes exactly once per point, which makes it better ground truth than anything in the player movement — and it is free. Two readers exist:

  • scoreboard watches the score box for a change that persists. Simple, but it can only ever report that something moved, so it cannot be checked.
  • scoredigits reads the numbers, without a font model. Within a game a cell counts 0, 1, 2, 3 and never goes back — so the k-th distinct appearance a cell settles into is the number k. That turns every detection into a claim you can check: the final tally must equal the score on the board.

The second is preferred for exactly that reason. It is checkable; the first is not.

The habits worth keeping

Three conventions run through the whole codebase, and they are the reason its numbers can be trusted.

Nothing is passed off as observed when it was not. Every position carries its provenance — measured, split from a merged blob, or predicted by the motion model. The CSV records it, the demo draws coasted positions as corner ticks rather than solid boxes, and the bird's-eye plan draws them as hollow circles. When the tool does not know, it says so instead of filling in.

Constants carry the measurement that set them. Nearly every threshold in detect/players.py has a comment giving the numbers behind it — often including what was tried first and why it failed. That is what stops the next person, or the next session, from re-litigating a settled question or quietly undoing a fix.

Fitted numbers are separated from honest ones. Where anything is tuned, it is scored on data it was not tuned on, and both figures are printed with the optimistic one labelled. The config files carry a note field saying which to quote.

Known limits

  • Ball tracking does not work. Resolved 0 of 14 labelled impacts on real footage. Not a tuning problem.
  • The score box is one broadcast's. Hard-coded fractions; a different production needs new ones.
  • Per-player statistics are not validated. Identity has been checked by eye on sampled frames and by the aggregate measures above, but never against hand labels naming which player took which shot.
  • Merges lose about 15% of rally frames. Prediction-guided splitting recovers some; the rest claim no position by design.
  • The court crop assumes a camera behind the court. Another angle needs COURT_ROI changed.
